# Mission Control → ERP — Phase 0 Foundation

This directory is the **Phase 0 foundation** from `MISSION_CONTROL_ERP_TRANSFORMATION_PLAN.md`:
it moves Mission Control off fragile JSON flat-files and onto a **transactional SQLite
database** with a real schema, a lossless migration, an immutable **audit log**, and the
**RBAC + clearance** spine a defense contractor needs — without touching the live app.

> **Safety:** everything here is additive and isolated on branch `erp-phase0`. Nothing in
> this folder modifies `server.js`, the live `*.json` data files, or any running service.
> The migration reads **copies** of the production data in `sample-data/` only.

---

## What's here

| File | Purpose |
|---|---|
| `schema.sql` | Full SQLite schema (37 tables) implementing the plan's §7 data model. WAL mode, declared FKs, indexes. |
| `migrate.js` | Loads the `sample-data/` JSON copies into `mc.db` and prints a reconciliation report. Idempotent (safe to re-run). Uses Node's built-in `node:sqlite` — **no external dependency**. |
| `dal.js` | Data-access-layer stub. Representative read/write functions that write an `audit_log` row on **every** mutation (the audit pattern Phase 0 mandates). |
| `mc.db` | The built database (regenerated by `migrate.js`). |
| `sample-data/` | Read-only copies of the live MC JSON, taken at build time. Source of the migration. |

## How to run

```bash
cd erp-foundation
node migrate.js        # Node 24+; drops & rebuilds mc.db, prints reconciliation
sqlite3 mc.db ".tables"
```

`node migrate.js` is idempotent — re-running produces the same DB and the same report.

## Source → table mapping

- **crm-data.json** — a flat, denormalized row (company + contact + deal combined). Migration
  **normalizes** it: one `company`, one `contact`, one `deal` per source row, keyed
  deterministically off the source id (e.g. `EXOS-0001`). This is the start of making MC the
  single CRM system of record.
- **tasks.json** → `task` (with `task_list`/`project`/`milestone` tables ready for Phase 2).
- **opportunities.json** → `opportunity` (kept distinct from CRM `deal` — BD pipeline vs. sales).
- **decisions.json** → `decision` (the Decisions inbox).
- **envelopes.json** → `document` (doc_type=`envelope`) + `document_signer` (one per signer).
- **users.json** → `user`; `role` (admin/manager/member/hr/finance/contracts) and `clearance`
  (hr-pii/itar-controlled/financial) are seeded for the RBAC × clearance matrix.

## Schema design notes

- **Lossless guarantee:** every table keeps a `raw_json` column with the full source record, so
  no field is ever dropped in the JSON→SQLite move.
- **Audit log:** `audit_log` captures actor, timestamp, entity, entity_id, action, and
  before/after JSON snapshots. Append-only by convention (the DAL never UPDATEs/DELETEs it).
  The 3,860 rows are the migration itself, logged.
- **RBAC + clearance:** two dimensions enforced together — `role` (what job) × `clearance`
  (what sensitivity: hr-pii / itar-controlled / financial). `user_clearance` is the M:N join.
- **Stubs (schema only, no data in Phase 0):** People (employee, org_unit, position, pto_*),
  Contracts (contract, wbs_element, deliverable/CDRL, contract_milestone, invoice),
  Procurement/Assets (vendor, purchase_order, po_line, receipt, asset, asset_event). These
  exist so Phases 1/4/5 add data, not tables.

## Phase 0 — remaining work (prioritized)

Phase 0's exit criteria (plan §5) are: all current features on SQLite, audit log capturing
changes, backups verified, one CRM of record. The data layer below is **done**; what's left:

1. **Cut the live server over to SQLite** *(Large)* — decompose `server.js` (~2,128 lines) into
   route modules + a data-access layer, and repoint `/api/*` reads/writes from the JSON files
   to `mc.db`. This DAL is the seed. Highest-effort item; the unlock for everything after.
2. **Audit + auth middleware on every `/api/*` route** *(Medium)* — single chokepoint that checks
   `role × clearance` and writes `audit_log` on every mutation (today auth is per-page).
3. **Resolve the two-CRM problem** *(Medium — decision-gated)* — MC CRM vs. the Supabase CRM must
   collapse to one system of record. **Needs Jon's call on which wins.**
4. **Clean the 18 duplicate IDs** *(Small)* — dedupe P-/FUND-/BD- collisions in the live data so
   they don't propagate. The migration already lists them.
5. **Backups, restore-tested** *(Medium)* — hourly WAL snapshot + nightly/weekly, 3-2-1 (ExoMac +
   backup node + encrypted offsite), monthly restore drill. Offsite target = GCC High (interim)
   then Azure Gov — gated on the Atomus quote.
6. **`KeepAlive` service** *(Small)* — run MC as a supervised launchd service so a reboot/crash
   auto-restarts and WAL replays cleanly (today it's a bare `node server.js`).

CMMC/CUI hosting (Azure Gov vs. ExoMac scoping) is sequenced **before Phase 1** when HR PII goes
live — it does not block items 1–6, which run on this non-CUI business data.
